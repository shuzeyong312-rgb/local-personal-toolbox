下面这版按你现在明确的真实使用场景重写：**不是运营分析系统，而是一个每天打开就能知道“今天哪些商品该出单、之前哪些单还没评价”的本地日历工具。**

# 《出单日历》功能 PRD V1.0

## 1. 产品定位

### 1.1 功能名称

**出单日历**

所属：个人工具箱 → 电商运营工具

### 1.2 核心用途

为商品制定周期性的出单计划，并通过月历管理每日任务。

用户每天上班打开后，可以快速确认：

* 今天有哪些商品计划出单
* 每个商品计划几单
* 今天是否已经完成
* 历史计划有没有漏掉
* 已出单的订单客户是否评价
* 哪些商品目前还有待评价记录

核心使用路径：

> 打开出单日历 → 看今天 → 完成后勾选 → 后续记录评价

不做复杂的数据分析、订单同步、利润计算和店铺管理。

# 2. 典型使用案例

商品：

**Y35 磁吸暖手宝**

开始日期：

**2026-09-16**

计划：

| 阶段  | 条件           | 出单频率  | 单次目标 |
| --- | ------------ | ----- | ---: |
| 阶段1 | 刚开始前3次       | 每天一次  |   1单 |
| 阶段2 | 累计实际出单未达到10单 | 每2天一次 |   1单 |
| 阶段3 | 累计实际达到10单后   | 每7天一次 |   1单 |

正常情况下日历会出现：

```text
09/16  Y35
09/17  Y35
09/18  Y35
09/20  Y35
09/22  Y35
09/24  Y35
……
```

每天打开软件，只需要看当天日期有没有 Y35。

完成后：

```text
Y35
计划：1单
实际：1单
状态：已完成
评价：未评价
```

客户之后评价：

```text
Y35
计划：1单
实际：1单
状态：已完成
评价：已评价
```

# 3. 产品原则

### 日历是绝对主界面

不能做成“计划列表 + 日历附属”。

用户进入这个工具后，第一眼就必须看到整个月日历。

### 今天必须最醒目

用户最常做的动作不是研究历史，而是：

> 今天要出哪几个品？

所以进入功能后：

* 自动跳转到本月
* 自动选中今天
* 自动展示今日任务

### 真实记录，不自动篡改历史

某一天没完成，就是：

**未完成**

不能自动改成第二天完成，也不能自动消失。

否则日历就失去了记录价值。

### V1 不上数据库

本地 JSON 足够。

不使用：

* PostgreSQL
* SQLite
* FastAPI
* ORM

减少开发、打包和维护成本。



# 6. 日期状态

日历日期至少需要区分：

| 状态     | 显示     |
| ------ | ------ |
| 无任务    | 普通日期   |
| 有待完成任务 | 任务标识   |
| 全部完成   | ✓      |
| 部分完成   | 部分完成标识 |
| 历史未完成  | !      |
| 今天     | 明显边框   |

不能完全依赖颜色。

例如：

```text
18
Y35 !
```

代表该日期已经过去，但 Y35 当天没有完成计划。

# 8. 出单状态

不建议单独让用户手动选：

> 待完成 / 部分完成 / 已完成

用户只填：

**实际出单数量**

系统自动判断。

例如：

| 计划 | 实际 | 状态      |
| -: | -: | ------- |
|  1 |  0 | 未完成/待完成 |
|  1 |  1 | 已完成     |
|  1 |  2 | 已完成     |
|  3 |  1 | 部分完成    |
|  3 |  3 | 已完成     |

内部状态：

```text
pending
partial
completed
skipped
```

# 9. 今日和历史的区别

如果今天：

```text
计划1单
实际0单
```

显示：

**待完成**

如果日期已经过去：

```text
计划1单
实际0单
```

显示：

**未完成**

也就是说状态文字根据日期动态变化。

不需要额外存一个 `failed`。

# 10. 快速完成

由于绝大多数计划可能都是：

> 计划 1 单

任务卡片直接提供：

**完成**

点击以后自动：

```text
actual_quantity = target_quantity
status = completed
```

这样日常不需要每次打开编辑框。

如果实际情况特殊，再点击编辑修改数量。

# 16. 为什么需要“初始已出单数量”

以后可能不是新品刚开始才加入工具。

例如 Y35 已经出了：

```text
6单
```

这时候才开始创建计划。

可以直接填写：

```text
当前累计实际出单：6
```

不用重新补历史数据。

# 17. 阶段规则

每个商品可以拥有多个阶段。

推荐不要使用“间隔几天”的表达。

统一使用：

> **每 X 天一次**

更不容易理解错误。

例如：

```text
阶段1

执行：3次
频率：每1天一次
每次：1单
```

等价：

**每天1单，共3次**

第二阶段：

```text
阶段2

结束条件：
累计实际出单达到10单

频率：
每2天一次

每次：
1单
```

第三阶段：

```text
阶段3

开始条件：
累计实际出单达到10单

频率：
每7天一次

每次：
1单

持续执行
```

---

# 18. 阶段类型

V1 只需要支持两种。

### 固定次数阶段

例如：

```text
3次
每1天一次
```

用于新品前三天。

### 累计数量阶段

例如：

```text
累计出单达到10单之前
每2天一次
```

达到数量后进入下一个阶段。

最后阶段：

```text
持续
每7天一次
```

---

# 19. Y35 实际配置

直接可以这样创建：

### 阶段1

```text
执行次数：3
每1天一次
每次目标：1单
```

### 阶段2

```text
直到累计实际出单：10单

每2天一次
每次目标：1单
```

### 阶段3

```text
持续

每7天一次
每次目标：1单
```

这与实际业务描述完全一致：

> 前三天每天1单 → 后面每隔一天1单 → 达到10单后每周1单。

---

# 20. 阶段切换规则

这里需要明确，否则开发时很容易写错。

**累计数量阶段以实际完成数量为准，而不是计划数量。**

例如：

计划：

```text
目前应该累计10单
```

但实际只完成：

```text
8单
```

那么仍然处于：

**阶段2**

不会因为计划日期已经排了10次，就自动进入每周一次。

---

# 21. 未完成是否补单

默认：

**不自动补。**

例如：

```text
09/20 Y35 应出1单
```

当天没有完成。

记录：

```text
09/20
Y35
未完成
```

不会自动给：

```text
09/21
Y35
补1单
```

这样历史才是真实的。

下一次仍根据当前阶段正常计算。

---

# 22. 达到阶段阈值后的处理

例如 Y35：

9 月 28 日完成后累计达到：

```text
10单
```

系统立即结束：

**每2天一次**

进入：

**每7天一次**

下一计划日期：

```text
09/28 + 7天
= 10/05
```

也就是下一阶段以：

**达到阈值的最后完成日期**

作为起点。

---

# 23. 未来日历生成

不能无限生成未来几十年的任务。

建议：

自动计算：

**未来 6 个月**

当用户切换到接近最后一个月时，再自动补充后续 6 个月。

但这些任务不一定必须全部写入 JSON。

优先方案：

> 根据规则动态计算未来任务，只保存实际发生过修改的任务记录。

这样 JSON 会非常干净。

---

# 24. 计划日期和任务记录分离

这是实现上最值得做的简化。

不要把未来几百个日期全部保存。

Plan 保存：

```text
计划规则
```

Record 保存：

```text
实际结果
```

日历打开时：

```text
规则
+
实际记录
=
最终日历
```

# 28. 暂停和结束的区别

### 暂停

暂时不继续生成任务。

历史数据保留。

以后可以恢复。

### 结束

计划正式结束。

不再产生未来任务。

历史继续存在。

### 删除

彻底删除该计划及记录。

需要二次确认。

日常使用更推荐：

**结束**

而不是删除。

---

# 29. 修改计划

编辑长期规则时：

### 过去

已经发生的历史全部保留。

### 今天及未来

按新规则重新计算。

例如 9 月 20 日修改 Y35：

```text
09/01～09/19
```

不能发生任何变化。

从：

```text
09/20
```

开始应用新规则。

# 35. 数据损坏恢复

# 44. 核心验收案例

创建：

```text
商品：Y35
开始：2026-09-16
```

规则：

```text
阶段1
3次
每1天一次
每次1单

阶段2
累计实际达到10单前
每2天一次
每次1单

阶段3
达到10单后
每7天一次
每次1单
```

首次应生成：

```text
09/16
09/17
09/18
09/20
09/22
……
```

9 月 16 日点击：

**完成**

结果：

```text
实际1单
累计1单
未评价
```

9 月 19 日客户评价：

点击：

**已评价**

结果：

```text
09/16
Y35
✓ 已完成
✓ 已评价
评价日期 09/19
```

如果：

```text
09/20
```

没有完成。

到了：

```text
09/21
```

09/20 必须仍然显示：

```text
Y35
!
未完成
```

不能自动消失。

当实际累计达到：

```text
10单
```

必须自动进入：

```text
每7天一次
```

并从最后一次完成日期开始计算下一计划日。

# 45. 最终验收标准

这个功能做完以后，应满足三个核心体验指标：

**每天打开后 3 秒内知道今天哪些商品需要出单。**

**完成一个任务最多点击 1 次。**

**可以随时查到某一天有没有完成，以及完成后的评价情况。**

只要这三个体验做顺了，这个功能就已经达到目标。不要继续往完整电商 ERP 的方向扩展。
