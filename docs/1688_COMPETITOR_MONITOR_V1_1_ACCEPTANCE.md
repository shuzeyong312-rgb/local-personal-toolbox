# 1688竞品监控 V1.1 正式验收准备报告

## 1. 验收结论

V1.1 已覆盖 PRD 规定的“竞品库 + 手动采集 + SQLite”范围，并通过服务层、界面层、持久化、异常隔离和真实页面采集检查。当前版本适合进入用户手工验收和真实日常试运行。

本次未开发 V1.2/V1.3，也未增加历史变化检测、自动任务、桌面通知或其他新功能。

## 3. SQLite 检查

| 检查项 | 结果 |
| --- | --- |
| 重启后数据仍存在 | 通过。测试关闭连接并用同一路径重新建立 `MonitorStore`，竞品名称、备注和快照完整保留 |
| 重复采集形成历史 | 通过。每次成功或部分成功采集均执行 `INSERT`，最新快照按采集时间和 id 读取 |

| 删除商品 | 符合 PRD。二次确认后通过级联外键删除该商品的快照和事件 |

## 7. 需要用户手工验证的步骤

以下步骤涉及真实桌面交互、本人登录态和长期使用感受，需要用户在正式数据库上确认：

1. 通过 `run.bat` 启动工具，打开“1688竞品监控”。
2. 确认专用 Chrome 已用 `9222` 调试端口启动、1688 已登录、官方采购助手已启用。
3. 添加一个新商品，填写竞品组、自定义名称和备注；确认首次采集完成后列表与详情数据正确。
4. 一次粘贴 2–3 个不同商品链接；确认全部添加并按顺序采集。
5. 再次添加其中一个带不同查询参数的链接；确认提示“商品已存在”，且没有重复商品。
6. 关闭工具并重新启动；确认商品、分组、名称、备注和最新快照仍存在。
7. 对同一商品执行两次“采集选中”；可通过后续 SQLite 检查或 V1.2 历史界面确认快照数增加，旧数据未覆盖。
8. 暂停一个商品，再执行“立即采集”；确认进度中不出现该商品。恢复后再次执行，确认重新进入队列。
9. 重命名分组，再删除分组；确认商品先显示新分组名称，删除后进入“未分组”，已有快照仍可见。
10. 临时关闭专用 Chrome 后采集一个商品；确认显示明确失败原因。重新启动 Chrome 后可再次成功采集。
11. 临时禁用官方采购助手或使用未出现助手的页面；确认失败原因明确指向官方采购助手。
12. 用 10 个 POC 商品执行一次批量采集，观察进度、取消剩余任务以及单个失败后的继续行为。
13. 连续实际使用 3–7 天，确认 50–200 个商品的串行耗时和页面稳定性可接受。

手工验收应使用真实业务数据库，但不需要清空或修改现有出单日历数据。

## 8. 已知限制

- 依赖本机专用 Chrome、有效的 1688 登录态、CDP 调试端口和官方采购助手。
- 页面或助手 DOM 改版后可能需要维护提取规则。
- V1.1 串行采集；商品较多时耗时与页面加载速度线性增长。
- 当前只读取可见 SKU 名称，不遍历完整组合，不保证全部 SKU、独立价格、库存或真实可售状态。
- 销售与成交数据是页面原始展示值，不代表精确销量或真实日增量。
- V1.1 仅显示最新快照；历史趋势、变化事件中心属于 V1.2，本次未实现。
- 自动运行和桌面通知属于 V1.3，本次未实现。

## 9. 是否建议进入 V1.2

暂不建议立即开始 V1.2。

V1.1 已达到用户手工验收和真实试运行条件。建议先完成上述手工步骤，并用 10 个 POC 商品连续运行 3–7 天。确认登录态、助手加载、批量耗时和字段稳定性没有阻断问题后，再明确批准进入 V1.2。

## 10. V1.1.1 稳定性与UI修正

### 修复的问题

- 瞬时页面加载失败过去需要用户手动重新采集；现在商品级自动进行一次轻量重试。
- 采集前过去要求用户手动启动调试 Chrome；现在任务先检查 CDP，必要时自动启动专用 Chrome。
- 环境故障过去可能表现为每个商品分别失败；现在环境状态属于整次任务，不覆盖商品已有状态。
- 默认错误过去直接暴露 Playwright、ECONNREFUSED 和 Call log；现在默认显示用户可理解的信息，原始内容放在“查看详情”。
- 列表过去没有店铺信息；现在显示可确认的店铺名称。
- 进度弹窗过窄、百分比可能被裁切；现在使用更宽弹窗、26px 高进度条和独立居中的百分比层。
- 添加、编辑、分组管理、删除、进度和错误窗口已统一为工具箱现有中文蓝白弹窗。

### 自动重试策略

- 每个商品最多尝试 2 次。
- 第一次发生页面加载异常、商品区未完整加载、采购助手未加载或核心字段大面积缺失时，等待约 2 秒后重试一次。
- 第二次结果作为最终结果；第二次成功时不记录第一次瞬时失败。
- 明确 HTTP 404、商品不存在或已下架等确定性错误不重试。
- 登录状态失效属于任务环境错误，不作为单商品失败重试。
- 不按 offer_id 编写特例，不使用指数退避，不引入并发。

### Chrome 自动启动策略

用户点击“立即采集”或“采集选中”后，任务先检查配置的 CDP 地址：

1. 已可连接：直接采集，不启动新 Chrome。
2. 不可连接：查找本机 Chrome，使用 `--remote-debugging-port=9222` 启动。
3. 等待 CDP 最多约 15 秒；就绪后自动继续采集。
4. 启动失败或超时：终止整次任务，不写入商品失败结果。

专用 Profile 固定为：

```text
C:\1688-monitor-profile
```

该 Profile 用于保留 1688 登录态和官方采购助手，不使用用户日常 Chrome Profile，也没有新增后台常驻服务。

### 登录失效处理

- 页面出现明确登录提示或跳转到登录路径时，任务显示“1688登录状态已失效，请在专用Chrome中重新登录后重试。”
- 提供“打开专用浏览器”按钮。
- 不自动处理账号登录、验证码、短信验证或安全校验。
- 登录失效会停止整批任务，不覆盖商品最新快照、商品状态或最近成功时间。

### shop_name 字段与覆盖情况

- `competitors` 新增可选字段 `shop_name`；旧数据库启动时自动执行兼容迁移。
- 数据只取最终可见 DOM 中唯一可确认的店铺标题，不使用推荐商品信息。
- 每次成功或部分成功采集读到明确值时更新当前店铺名。
- 本次缺失时保存逻辑不会清空数据库已有店铺名。
- 店铺名不属于核心字段，缺失不影响 success；主列表显示 `--`。
- 主列表新增“店铺”列，完整名称可通过鼠标悬停查看。
- 2026-09-17 真实商品 `976443859503` 回归读取为“佛山淘趣科技有限公司”，价格列表、原始销量和 9 个可见 SKU 语义均未改变。

### 进度弹窗调整

- 最小宽度调整为 650px，进度条高度调整为 26px。
- 百分比使用独立前景标签水平、垂直居中，蓝色进度块使用浅色以保证可读性。
- 自动测试覆盖 `0%`、`10%`、`60%`、`80%`、`100%`。
- 保留“正在监控 X / Y”和原有计算规则：处理第 4/5 个商品时，前三个已完成，显示 60%。
- 商品名称优先；没有名称时 worker 回退 offer_id；超长名称使用省略号截断。
- 完成后关闭进度弹窗，汇总成功、部分异常和失败数量。

### 弹窗 UI 统一

- 添加和编辑竞品使用统一的 `BaseDialog`、中文“保存/取消”。
- 分组管理改为自有列表窗口，使用中文“新建/重命名/删除/关闭”，不再调用系统 `QInputDialog`。
- 删除确认、普通提示、环境错误和技术详情使用统一弹窗，不再出现英文 OK/Cancel。
- 主操作沿用现有蓝色按钮；输入框、内边距、圆角和按钮高度复用工具箱主题。

### 错误信息分层

- 用户层示例：采集浏览器启动失败、登录状态失效、页面加载失败、采购助手未加载、商品数据未完整加载。
- 技术层保留原始 Playwright 异常、网络错误、Call log、URL 和 DOM/缺失字段诊断。
- 商品失败技术详情随事件保存到 SQLite；界面默认隐藏，通过“查看详情”打开。
- 环境失败技术详情保存在 `monitor_runs.error_summary`，环境提示中可主动查看。

### 商品状态与任务状态

- 商品状态使用正常、部分异常、最近采集失败和暂停；旧数据库中的“采集失败”会兼容迁移为“最近采集失败”。
- `monitor_runs` 记录 preparing_environment、completed、environment_failed、cancelled 等任务结果。
- Chrome 启动失败或登录失效时不发送商品完成信号，因此不会批量污染商品状态。
- 普通单商品失败仍保存到该商品，并继续处理批量中的下一个商品。
