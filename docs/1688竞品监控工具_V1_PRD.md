# 1688竞品监控工具 V1 PRD

> 文档状态：V1.0  
> 产品类型：个人电商运营辅助工具 / 本地桌面工具箱模块  
> 核心原则：免费、本地、低复杂度、低维护成本、允许字段缺失、不追求商业级高可用  
> 数据来源：1688商品详情页 + 已安装的“1688官方采购助手”最终渲染 DOM  
> 数据库：SQLite  
> 采集方式：复用专用 Chrome 登录态，通过 Playwright/CDP 读取页面最终渲染内容

---

## 1. 背景

日常竞品观察目前依赖人工打开1688商品页面，逐个查看价格、起批量、SKU、销量和官方采购助手中的月成交、年成交等信息。

当竞品数量达到约 50–200 个后，人工重复检查存在以下问题：

- 很难每天稳定检查全部商品；
- 很难记住昨天的价格、SKU和销量展示值；
- 价格、SKU发生变化时容易错过；
- 无法形成长期历史记录；
- 无法快速识别“今天哪些竞品发生了值得关注的变化”。

因此需要在现有个人工具箱中增加一个“1688竞品监控”工具，自动记录公开页面数据、比较历史变化并生成提醒。

## 3. 产品定位

### 3.1 产品定义

1688竞品监控工具不是“1688商业数据平台”，而是：

> 每天自动记录竞品公开页面状态，通过历史快照发现价格、SKU和销售展示指标的变化，并辅助日常运营判断。

### 3.2 核心问题

工具主要回答三个问题：

1. **今天哪些竞品发生了变化？**
2. **某个竞品最近的价格、SKU、销售展示指标如何变化？**
3. **哪些变化值得我立即关注？**

### 3.3 非目标

V1 不承诺：

- 真实日销量；
- 精确月销量；
- 精确库存；
- 所有SKU价格；
- 所有商品所有字段100%永久可用；
- 1688页面未来改版后无需维护。

## 4. 用户与使用规模

### 4.1 用户

单用户，本地个人使用。

### 4.2 目标规模

- 竞品数量：50–200个；
- 采集频率：每天1次；
- 默认采集时间：09:00；
- 历史数据：默认永久保存。

### 4.3 运行原则

- 不购买第三方API；
- 不部署云服务器；
- 不使用 PostgreSQL、Redis、消息队列等重型基础设施；
- 数据全部保存在本机 SQLite；
- 采集串行执行，不做并发高频访问。

## 5. V1版本拆分

V1 分三个小阶段开发，不一次性完成全部功能。

### V1.1：竞品库 + 手动采集 + SQLite

目标：先跑通“添加竞品 → 手动采集 → 保存历史快照”。

包含：

- 单链接添加；
- 多链接批量添加；
- 自定义竞品组；
- 自定义名称；
- 备注；
- 暂停/恢复监控；
- 手动“立即采集”；
- SQLite保存；
- 最近一次数据展示；
- 采集成功/部分成功/失败状态。

### V1.2：历史变化 + 今日监控

目标：让历史数据真正产生运营价值。

包含：

- 价格变化检测；
- SKU新增/删除检测；
- 销售展示值变化检测；
- 官方采购助手指标变化记录；
- 今日监控面板；
- 异常事件列表；
- 商品详情历史趋势；
- 7天 / 30天 / 90天 / 365天范围切换。

### V1.3：自动运行 + 桌面提醒

目标：从“手动工具”变成日常自动辅助工具。

包含：

- 每天09:00自动采集；
- 开机后漏采补采；
- Windows桌面通知；
- 价格提醒阈值；
- 销售展示值跃升阈值；
- 连续采集失败提醒。

## 7. 核心用户流程

### 7.1 添加竞品

流程：

```text
粘贴1个或多个1688商品链接
        ↓
校验是否为1688商品详情链接
        ↓
提取 offer_id
        ↓
检查是否已存在
        ↓
选择竞品组
        ↓
可选填写自定义名称 / 备注
        ↓
执行首次采集
        ↓
保存商品 + 第一条快照
```

规则：

- 同一 offer_id 不允许重复添加；
- 重复链接提示“商品已存在”，并跳转已有商品；
- 首次采集失败时，可以保存链接，但状态标记为“待验证”。

| 字段 | 说明 |

### 8.1 自定义竞品组

支持：

- 新建组；
- 重命名；
- 删除组；
- 商品移动分组。

删除分组时：

- 不删除商品；
- 商品移动到“未分组”。

### 8.2 暂停监控

暂停后：

- 不进入自动采集队列；
- 历史数据保留；
- 可以随时恢复。

## 10. 价格模型

### 10.1 原则

V1不再把“价格”理解成一个单一数字。

必须保存页面实际展示的价格列表：

```json
["¥125.00", "¥117.00", "¥110.00"]
```

不得自动选择：

- 最低价；
- 最高价；
- 第一个价格；
- 所谓“主价格”。

### 10.2 price_tiers

只有数量与价格可以明确对应时，保存：

```json
[
  {"qty_raw":"1件起批","price_raw":"¥125.00"},
  {"qty_raw":"100-999件","price_raw":"¥117.00"},
  {"qty_raw":"≥1000件","price_raw":"¥110.00"}
]
```

无法可靠对应时：

```json
"price_tiers": []
```

但 `price_raw_values` 仍正常保存。

### 10.3 展示价格区间

为了趋势图展示，可以从 `price_raw_values` 中解析数字，生成派生值：

- display_price_min
- display_price_max

这两个字段仅用于图表：

> “页面展示价格区间”

不得命名为“真实成交价”。

## 11. 销量与成交指标模型

这是V1最重要的口径限制。

### 11.1 不创建“真实日销量”

页面存在：

```text
已售80+台
月成交10+
年成交70+
```

这些都是1688页面/官方助手的原始展示值。

V1：

- 保留原始字符串；
- 可以解析数值下界用于变化辅助；
- 不将“80+”当成精确80；
- 不把两天数值下界差直接称为“日销量”。

### 11.2 派生结构

例如：

```json
{
  "sales_raw": "已售80+台",
  "sales_lower_bound": 80,
  "sales_value_type": "gte"
}
```

`<10`：

```json
{
  "lower_bound": 0,
  "upper_bound": 10,
  "value_type": "lt"
}
```

### 11.3 UI命名

使用：

- 页面已售
- 销售展示值
- 销售展示趋势
- 月成交展示
- 年成交件数展示

避免使用：

- 今日真实销量
- 精确月销量
- 精确年销量

## 12. 历史快照

### 12.1 采集策略

每次采集都生成一条 Snapshot。

允许一天内手动采集多次。

趋势图按天展示时：

> 默认使用当天最后一次成功快照。

历史原始快照不覆盖。

### 12.2 快照时间

字段：

```text
collected_at
snapshot_date
```

### 12.3 数据缺失

如果某天未成功采集：

- 不补造数据；
- 不进行线性插值；
- 图表显示缺口；
- 次日数据不能直接宣称为“日增量”。

## 13. 价格变化检测

### 13.1 所有变化均记录

比较：

```text
previous.price_raw_values
current.price_raw_values
```

只要不同：

> 生成价格变化事件。

### 13.2 可以计算百分比的场景

仅以下场景计算百分比：

**场景A：单价格 → 单价格**

```text
¥79 → ¥74
```

**场景B：相同 qty_raw 的 price_tier**

```text
≥1000件
¥110 → ¥100
```

计算：

```text
变化率 = (新价 - 旧价) / 旧价
```

### 13.3 无法可靠比较

如果：

```text
["¥45", "¥50"]
→
["¥42", "¥48", "¥52"]
```

只记录：

> 价格结构发生变化

不擅自计算百分比。

### 13.4 提醒规则

默认：

- 所有价格变化：记录；
- 可可靠计算且绝对变化率 ≥ 5%：桌面提醒；
- 价格结构变化但不可计算百分比：只记录，不默认提醒。

阈值允许用户修改。

---

## 14. SKU变化检测

### 14.1 比较对象

比较：

```text
visible_sku_names
```

进行集合差异。

### 14.2 事件

例如：

```text
昨日：
白色
黑色
粉色

今日：
白色
黑色
粉色
绿色
```

生成：

> 新增SKU：绿色

删除同理。

### 14.3 规则

- 去除首尾空白后比较；
- 保留原始名称；
- 不自动猜测“改名”；
- “旧SKU删除 + 新SKU新增”按两个事件处理；
- SKU新增/删除默认触发桌面通知。

V1不自动切换SKU验证完整组合。

---

## 15. 销售展示值变化

由于数据是 `<10`、`10+`、`80+台` 等模糊展示值，V1不实现“精确销量突增”。

改为：

> **销售展示值跃升**

### 15.1 基础事件

若：

```text
sales_raw
```

发生变化：

> 记录“页面已售展示发生变化”。

### 15.2 可解析下界

若前后均能解析 lower_bound：

```text
80+ → 120+
```

派生：

```text
展示下界变化 = +40
```

UI明确标注：

> “展示下界 +40，不等于真实新增40件”。

### 15.3 默认提醒

V1.3 默认规则：

```text
展示下界增加 >= 20
```

触发：

> 销售展示值明显跃升

该阈值可修改。

不再采用原计划中的：

> “真实日销量 + 7日平均 + 150%增长”

因为当前数据源不足以支持该精度。

## 22. 采集状态定义

### success

所有V1核心字段采集成功。

### partial

页面可正常访问，但一个或多个核心字段缺失。

示例：

```text
价格缺失
月成交缺失
```

仍保存该次快照。

### failed

无法形成有效商品快照，例如：

- Chrome无法连接；
- 页面加载失败；
- 商品不存在；
- 官方采购助手未出现且核心助手字段无法读取；
- 登录状态明显失效。

## 35. 最终产品原则

开发过程中始终遵守：

1. **原始数据优先于推测。**
2. **无法确认时显示缺失，不猜。**
3. **价格允许多值，不强行压成一个数字。**
4. **模糊销量不能包装成精确销量。**
5. **核心监控是价格、SKU和公开销售指标变化，不是做商业BI。**
6. **一个通用规则能解决的问题才进入采集层；不要为个别商品堆特例。**
7. **个人使用优先：本地、免费、简单、可维护。**
8. **先完成V1.1，再决定是否继续V1.2；先完成V1.2，再启用V1.3自动化。**
